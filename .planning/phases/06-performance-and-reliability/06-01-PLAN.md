<objective>
Phase 6 is the first non-infra phase: two surgical reliability fixes to real application logic across six files, no view change, no new dependency.

1. **PERF-01 — kill the N+1 in `SaleController::productsMeta()` (D-01/D-02).** The method currently runs 3 queries PER product inside a `foreach` over `allForUser` (`lotsForProduct`, `purchasedQty`, `soldQty`) — O(3N) queries. Replace with **3 fixed queries** regardless of product count: `Product::allForUser` (unchanged), a new `Purchase::lotsForUser` (all lots, 1 query), and a new `Sale::soldQtyByProduct` (GROUP BY, 1 query). Group the batched lots by `product_id` in PHP; per product compute `purchasedQty = SUM(quantity)` of its lots, `cump = ProfitCalculator::cump($lots)` UNCHANGED, `stock = ProfitCalculator::stock($purchasedQty, $sold[$pid] ?? 0)`. Per-product output (adds `cump`, `stock`) must be byte-identical — `sales/form.php` is untouched. CUMP is NEVER computed in SQL; ProfitCalculator is NEVER modified.

2. **PERF-02 — harden `ExchangeRateService` and make the server authoritative about a valid FX rate (D-03/D-04/D-05).** Rewrite `ExchangeRateService::latest()` from `file_get_contents` (may be blocked on Lambda when `allow_url_fopen` is off, never logs, never checks HTTP status) to **curl** with a 5s connect+transfer timeout, mirroring `CloudinaryStorage`'s idiom but returning `null` (not throwing) and checking `!== 200` (not `>= 400`). Then in `PurchaseController::validate()` (which both `store()` and `update()` call), when a non-EUR purchase's submitted rate is missing/`<= 0`, attempt a lazy server-side fallback fetch; if it returns a rate `> 0`, use it; if it returns `null`, **block** the submission with a clear French flash error and `return null` BEFORE `ProfitCalculator::unitCostEur()` — so a 0.00/wrong EUR cost can never be written.

**Known gap (OUT OF SCOPE, D-06):** `OrderController::persistLines()` also computes `unit_cost_eur` from a submitted rate (validated with the same `$rate <= 0` guard in `parseInput()`) but has **no** server-side fallback. Per D-06 this is explicitly NOT fixed in this phase. The risk is unchanged from today (the rate field is required; the user must supply it) — it is documented here and in the threat model so a future phase can close it, and must NOT be touched by this plan.

Purpose: the sale form loads fast at any catalog size, and a USD purchase is never silently corrupted into a 0.00 cost when frankfurter.app is slow or down.

Output: six modified/created files (two model methods added, one private controller method rewritten, one service rewritten, one controller guard extended, one new test). PERF-01 is a correctness-preserving data-access refactor (same numbers, far fewer queries) verified by the existing ProfitCalculator suite staying green + structural greps + a post-deploy visual smoke. PERF-02's identity path gets a real network-free unit test (`ExchangeRateService` is in `phpunit.xml`'s `src/Services` coverage scope); its curl/fallback/block paths are I/O and verified by post-deploy smoke. All live proofs are folded into `<verification>` for the orchestrator to run after deploy — this is a single autonomous plan with no operator/Wave-2 half.
</objective>

| Purchase form (browser) → PurchaseController::validate() | Untrusted `currency` + `exchange_rate` cross here. Currency is allowlisted (`in_array(['EUR','USD','CNY'], true)`) before use; the submitted rate is validated `> 0` and overridden by a server-side fetch when invalid. |
| PHP runtime → frankfurter.app (server-side curl) | The app now calls the FX API server-side for the first time. The URL host is hardcoded (`https://api.frankfurter.app/latest`); only the allowlisted, urlencoded `from`/`to` currency codes are appended — no user-controlled host. |

| FX rate → unit_cost_eur write | A non-positive/absent rate must never produce a persisted cost; the D-05 block is the guarantee. |
