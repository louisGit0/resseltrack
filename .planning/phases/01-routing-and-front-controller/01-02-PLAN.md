<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Local repo → GitHub (public/private) | Pushed history must not contain secrets |
| GitHub → Vercel build/deploy | Repo contents enter the build environment; secrets must not be present |
| Vercel deployment → public internet | The app and its static assets become publicly reachable over HTTPS |

This phase introduces no new auth/input surface (`public/index.php` unchanged). The deployment is intentionally configured with NO env vars, so no live DB or session secrets exist yet. No high-severity threats expected.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-04 | Information Disclosure | Secrets in pushed git history | mitigate | `.env` is gitignored and absent from the repo; Task 1 acceptance criteria assert `.env` is not in the GitHub repo. No secrets are added as Vercel env vars this phase. |
| T-1-05 | Spoofing/Tampering | GitHub → Vercel integration trust | accept | Standard OAuth integration on the operator's own accounts; Hobby plan, single operator. Low risk. |
| T-1-06 | Denial of Service | Assets routed through PHP inflating invocations | mitigate | DEPLOY-02 check confirms CSS/JS are served by the CDN (no `x-powered-by: PHP`), so static requests never invoke the function. |
| T-1-SC | Tampering | npm/composer package installs | accept | No local package installs in this phase. `vercel-php@0.7.4` is Vercel-managed (referenced in vercel.json). No legitimacy checkpoint required. |

Deferred (NOT Phase 1 blockers): HSTS (SEC-02, Phase 5), `SESSION_SECURE=1` (Phase 3), CSP for R2 (SEC-03, Phase 5). The live site is not intended for real end-user use until those land.
</threat_model>
