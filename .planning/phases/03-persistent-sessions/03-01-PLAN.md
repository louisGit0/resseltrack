<objective>
Deliver the entirely-autonomous code half of Phase 3: replace PHP's file-based session save handler with a MySQL-backed one. (1) Create `src/Core/DatabaseSessionHandler.php` implementing `\SessionHandlerInterface` over the existing `Database::connection()` PDO singleton (SESS-02). (2) Wire it into `Auth::start()` before `session_start()` and switch the cookie to a 30-day persistent lifetime while keeping the production security flags (SESS-01, SESS-03). (3) Add the `sessions` table to both `sql/schema.sql` and `Schema::ensure()`, and disable PHP's probabilistic GC in `api/php.ini` (SESS-02 storage substrate, D-04).

Purpose: This is the autonomous half — pure PHP + SQL + one ini line, all locally lintable. SESS-04 (CSRF) requires NO code change: once `$_SESSION` is MySQL-backed, the CSRF token at `$_SESSION['_csrf_token']` persists transparently (D-07). Wave 2 (Plan 03-02) is the operator half: re-run `bin/migrate.php` against Aiven, set `SESSION_SECURE=1` in Vercel, redeploy, and verify SESS-01..04 live.

Output: New `src/Core/DatabaseSessionHandler.php`; modified `src/Core/Auth.php`, `src/Core/Schema.php`, `sql/schema.sql`, `api/php.ini`. No new Composer packages. No changes to `Csrf.php` or `Auth::login()`/`logout()`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser cookie → app | The session ID travels in the `RESELLTRACK_SESS` cookie; flags must prevent JS access and cross-site leakage |
| App → MySQL sessions table | Serialized `$_SESSION` (incl. user_id, CSRF token) is written/read over the Phase 2 TLS PDO |
| Old session ID → new session ID (login) | `session_regenerate_id(true)` must atomically destroy the old row and write the new one with no orphan |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-01 | Elevation of Privilege | Session fixation at login | mitigate | `session_regenerate_id(true)` in `Auth::login()` (unchanged, D-08) drives the handler's `destroy(old)`+`write(new)`; no orphan row (RESEARCH Pattern 2 / RQ2). Verified live in 03-02. |
| T-3-02 | Spoofing | Session hijacking via cookie theft | mitigate | Cookie flags `Secure` (from SESSION_SECURE, set in 03-02 D-10) + `HttpOnly` + `SameSite=Lax` (D-05, Task 3). 30-day TTL bounds exposure. |
| T-3-03 | Tampering | CSRF on the new store | mitigate | `$_SESSION['_csrf_token']` persists transparently once MySQL-backed; `Csrf::validate()` unchanged (D-07). Verified by a real POST returning no 419 in 03-02 (SESS-04). |
| T-3-04 | Information Disclosure | Direct read of the sessions table | mitigate | Table access is via the app's least-privilege MySQL user over TLS only; no session data is exposed through the application layer. Payload is non-sensitive app state (RESEARCH Security Domain). |
| T-3-05 | Denial of Service (storage) | Orphan/expired session rows bloating the DB | mitigate | Lazy read-time expiry (`WHERE expires_at >= UNIX_TIMESTAMP()`) hides expired rows; `gc()` + `idx_sessions_expires` enable explicit bulk cleanup (D-04, Task 1/Task 2). |
| T-3-SC | Tampering | npm/composer package installs | accept | No package installs this phase — pure PHP + SQL + one ini line (RESEARCH "Package Legitimacy Audit: not applicable"). No legitimacy checkpoint required. |
</threat_model>
