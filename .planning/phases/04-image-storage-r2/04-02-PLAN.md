<deploy_note>
Unlike Phase 3 (where the new session handler ran on EVERY request), Phase 4's R2 code only runs on image upload/delete actions. So there is NO broken-auth window: if the code deploys before the R2 env vars are set, normal pages still work and only uploads fail (R2Storage throws on missing creds → the user sees the generic French upload-failure message). Recommended order anyway: set the 5 R2_* env vars BEFORE (or together with) the redeploy so the first build that installs aws-sdk-php also has working creds. This is also the FIRST deploy that runs `composer install` (aws-sdk-php) — watch the Vercel build logs to confirm the build succeeds and vendor/ is bundled.
</deploy_note>
</context>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-4-07 | Information Disclosure | R2 secret in env vars | mitigate | R2_ACCESS_KEY_ID + R2_SECRET_ACCESS_KEY are Vercel Sensitive env vars + operator local .env (gitignored); never committed (SEC-01, D-09). |
| T-4-08 | Spoofing/Tampering | R2 API token over-scoped | mitigate | Token scoped to Object Read & Write on the single bucket — least privilege. |
| T-4-09 | Information Disclosure | Public bucket exposes unrelated objects | accept | Only app-generated random-keyed product images are written; the dev URL is rate-limited; no sensitive data stored as images. |
| T-4-SC | Tampering | composer install at build | mitigate | aws/aws-sdk-php is [OK]/Approved (RESEARCH legitimacy audit); pinned ^3; Packagist-resolved by Vercel's managed build. |
